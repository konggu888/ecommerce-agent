版本日期：2026-10-15

## 1. 目的与边界

本审查用于回答：现有规划、代码、测试、UI、帮助文档和恢复机制，是否足以指导 AI 将桌面应用做成普通用户能理解、能安全操作、能恢复异常，并能获得符合明确质量标准的商业视频产品。

这不是另起一套路线图，也不是新增一批未经核实的验收编号。它是 PLAN-003 的完整性检查入口，先识别已有要求、重叠要求、缺口和证据不足，再将确有必要的独立要求映射回正式验收计划和总台账。

### 明确不做

- 不新增产品功能，不修改产品代码，不为增加任务数量而拆分任务。
- 不因本文建立就认定任何功能已实现、已验收或项目完成率提高。
- 不删除或重编号 A0–A112；发现同义项必须先保留原 ID 并建立映射。
- Windows 真机、真实素材、真实 Provider/实际扣费、剪映现场、真实投放和商业效果验证继续暂缓。
- PR #32 必须保持 Open / unmerged。
- 总体完成率、权重和 fully_audited 口径继续关闭，直到 PLAN-003 完成规定审计。

## 2. 审查的八个维度

1. **新手可理解性与可发现性**：首次打开、入口可见性、术语解释、默认路径、简单模式/高级设置边界、空状态和操作反馈。
2. **端到端用户旅程**：创建项目、商品输入与核实、目标/策略、预算确认、资产准备、分镜、逐镜头生成/修改、剪辑、质检、修复、交付、保存与再次打开。
3. **费用与外部副作用安全**：预估和确认时点、取消零调用、重复点击/重试、超时后结果不确定、账本失败、预估与实际费用差异、预算告警与用户选择。
4. **数据、素材与版本安全**：自动保存、崩溃恢复、备份/迁移、磁盘不足、损坏数据、项目隔离、版本隔离、路径变化、删除/覆盖保护、引用关系与资产可追溯。
5. **商品真实性、内容风险与交付闸门**：商品外观/结构/功能/用法事实边界、未验证声明、禁用/高风险表达、视觉复核证据有效性、交付文件完整性、1080P尺寸与真实清晰度区别。
6. **跨功能状态与依赖一致性**：修改商品/演员/场景/分镜/比例/音乐后，哪些下游结果失效、哪些可复用；任务并发、版本切换、状态机、稳定 ID 和旧结果隔离。
7. **异常解释与可恢复性**：错误归因、可重试性、恢复旧有效结果、部分成功、外部服务不可用、资源不足、退出/重启、人工决策与必须阻断的情况。
8. **结果可理解性与商业质量**：用户能看到阶段、待办、风险、费用、失败原因和下一步；同时区分运行正确、流程正确、商品表达正确、商业成片质量，不能用 CI 或分辨率替代主观/真实媒体验收。

## 3. 以用户旅程为主线的检查表

每个阶段都检查：输入与前置条件、用户能理解的提示、状态/持久化、副作用、正常路径、边界与异常、恢复/撤销、测试证据、帮助文档、剩余真实环境限制。

| 阶段 | 必核问题 |
|---|---|
| 首次启动/新建项目 | 用户知道从哪里开始吗？取消、重复点击、无权限、目录不可写如何处理？ |
| 商品输入/事实确认 | 链接解析失败是否有替代输入方式？哪些事实有来源、哪些未经验证？ |
| 目标与创意策略 | 不懂专业术语的用户能否让 AI 推荐并理解原因？用户能否纠正推荐？ |
| 预算与费用确认 | 费用拆分是否清楚？取消是否保证没有云端副作用？不确定/超时调用如何对账？ |
| 演员/场景/商品资产 | 用户能否识别和复用素材？资产被移动/删除/禁用后如何处理？商品真实素材与生成素材是否清楚区分？ |
| 分镜与镜头生产 | 用户知道每镜头状态、来源、成本和重试后果吗？单镜头修改是否只影响指定范围？ |
| 剪辑/字幕/音频 | 失败是否保留旧成片？音画、字幕、转场和画幅问题是否可见且可修？ |
| 质量/安全检查 | 每个阻断项有原因、证据和可执行的修复路径吗？待人工核验是否会被误当作通过？ |
| 最终交付 | 损坏/空文件/尺寸不合格/风险未处理时是否阻止交付？通过后能否追溯版本、素材和费用？ |
| 重新打开/长期使用 | 项目、版本、审核、成本、资产路径是否一致？迁移/升级/恢复是否有明确策略？ |

## 4. 风险等级与处置原则

- **P0 阻断性风险**：可能造成未经确认的费用/重复扣费、不可恢复数据丢失、跨项目或跨版本污染、危险/虚假商品表达被放行、损坏成片被标记可交付。必须先阻断或恢复安全状态。
- **P1 高风险缺口**：核心流程无法继续、用户无法理解费用/失败/风险、旧有效结果保护不足、关键状态不可追溯。应在依赖其上的阶段继续前处理或明确隔离。
- **P2 重要体验/质量缺口**：可绕过但明显增加误操作、困惑或产出质量不稳定。进入正式排期，需有验收标准。
- **P3 改进项**：便利性、说明文案或非关键效率问题。只登记，不顺手开发。

等级需依据可观察的损害、发生概率、可逆性、影响范围和现有缓解措施判定；不得仅凭主观严重感。未知证据标为“待核实”，不能直接标为安全或不安全。

## 5. 功能安全矩阵要求

对每个风险场景至少记录：
- 场景/触发条件；
- 用户可见行为和预期状态；
- 数据、文件、费用或外部调用副作用；
- 保护机制及失败关闭策略；
- 旧有效结果是否保留；
- 可恢复/需用户决定/必须阻断的分类；
- 对应代码入口、专项测试及当前 HEAD 证据；
- UI 可见反馈与帮助文档位置；
- 真实环境限制；
- 风险等级、正式任务 ID、重复/依赖映射和未决问题。

## 6. 与现有 A0–A112 的映射规则

1. 先检查正式验收计划、SOP、路线图、未来功能备忘、进度台账、执行控制、SESSION_HANDOFF、AI_HANDOFF、HELP 和 PROJECT_LOGIC。
2. 对每个发现标注：已有明确覆盖 / 相关但合同不同 / 重复登记候选 / 文档冲突 / 证据不足 / 可能的独立缺口。
3. 只有找到当前代码和测试证据，才能判定“已有覆盖”；仅有文档文字不算实现证据。
4. 语义相近不等于同一验收合同。保留独立失败条件、状态转换、数据范围或真实环境要求的任务，不得合并。
5. 不删 ID、不补造编号、不在审计前给新任务分配权重。确认为独立缺口后，先在台账记录建议，再依执行控制协议决定如何纳入正式计划。
6. 证据状态严格分开：静态映射、专项测试存在、当前 SHA 自动化运行、模拟端到端、真实环境验收、正式验收结论。
7. CI 绿灯只证明当前提交被工作流覆盖的自动化检查通过，不证明 UI 真实可用、费用真实正确、媒体真实合格或商业效果达标。
