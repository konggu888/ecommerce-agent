# AI 开发执行控制协议（强制）

适用仓库：`konggu888/ecommerce-agent`；项目：`apps/ad-studio-desktop`。
战略路线唯一来源：`docs/AD_STUDIO_PRODUCT_ROADMAP.md`；验收来源：`docs/AD_STUDIO_ACCEPTANCE_PLAN.md` 与 `docs/AD_STUDIO_ACCEPTANCE_SOP.md`；总进度入口：`docs/AD_STUDIO_PROGRESS_DASHBOARD.md`。

## 一、计划层级
1. 产品路线图定义产品终点、模块边界、阶段顺序与阶段退出条件。
2. 阶段计划列出目标、任务、依赖、进入/退出条件、风险和暂缓项。
3. 功能计划定义输入/输出、状态变化、实际生产链、异常路径与可验证行为。
4. 单次任务单只授权本轮明确范围。
5. 验收证据记录测试、当前 SHA 的 CI/doc-sync 和真实环境证据。
6. 总进度台账记录唯一任务 ID、状态、依赖、权重、证据与剩余条件。

文件冲突时先停止受影响的工作，列明冲突并修订正式计划；不得自行选择最方便的解释。

## 二、每次“推进”前的强制步骤
1. 先读 `apps/ad-studio-desktop/SESSION_HANDOFF.md`。
2. 再读 AI handoff、本协议、总进度、路线图、验收计划/SOP、AGENTS、HELP 与 PROJECT_LOGIC。
3. 查 GitHub 实时 HEAD、PR #32 状态与 head SHA；PR #32 必须保持 Open / unmerged，禁止擅自合并。
4. 查当前 HEAD 的 CI Push、CI PR、docs-sync Push、docs-sync PR 四项；运行中不算通过，失败先读日志修复，旧 SHA 不能替代新 SHA。
5. 检查代码、测试、UI、文档和依赖，确认是否已有实现或存在阻断。
6. 从总进度台账选择唯一下一项；全量盘点未完成时先盘点，不得凭感觉挑新功能。
7. 开始修改前写明任务目标、范围、排除项、依赖、测试、文档、验收条件、失败处理与停止条件。

## 四、禁止联想式扩展
1. 每轮只做一个主要任务及必要依赖/阻断修复。
2. 非阻断的新问题只登记待办，说明影响与建议优先级，不顺手实现。
3. 不得为了功能数、测试数或“架构完整性”创造没有实际价值的任务。
4. 不得重复实现已有功能；先查代码、测试和证据。
5. 不得通过改名、反复拆分或追加无关验收点让任务无限延长。
6. 改变产品目标、阶段顺序、用户确认的约束或暂缓范围，必须先取得用户批准。
7. 满足预先验收条件即结束当前任务，其他改进另行排队。

## 五、开发与验收状态分开记录
开发状态：未盘点、未开始、进行中、代码完成、阻塞、暂缓、取消。
验收状态：未验收、自动化待运行、自动化失败、自动化通过、模块集成通过、模拟端到端通过、待真实环境验收、正式验收通过、部分通过。
代码已写但测试未运行不得标记自动化通过；CI 只支持当前 SHA 覆盖的自动化结论；暂缓项仍保留在范围内，不能默默从分母删除或当作通过。

## 六、任务和阶段的停止条件
任务满足预定功能条件、实际生产链接通、必要测试通过、当前 SHA 四项 CI/doc-sync 成功、文档同步、未验证边界和回退路径均已记录，才可标记“自动化阶段完成”。阶段必须逐条满足路线图退出条件，否则保持进行中并列出缺口。

## 七、文档同步
桌面代码/测试改动必须同一提交更新：AGENTS.md、HELP.md、PROJECT_LOGIC.md、验收计划、验收 SOP、SESSION_HANDOFF.md、AI handoff、未来功能备忘。路线图变化时同时更新路线图。规划体系变更应同步受影响入口；避免无意义地重复追加同一状态。

## 八、用户约束
PR #32 不合并。Windows 真机、真实素材、真实 Provider、实际扣款/账单核对、剪映现场、真实投放数据和商业效果验收继续暂缓，除非用户明确允许。最终输出最低 1080P 级：竖屏 1080×1920、横屏 1920×1080、方形 1080×1080；像素放大不等于细节恢复。

## 九、每轮结束报告
报告任务 ID、范围、实际修改、测试/失败修复、最新 SHA、四项 CI/doc-sync、PR 状态、开发/验收状态、未完成/暂缓项、台账变化和下一项正式任务。没有执行的测试不得声称通过。
