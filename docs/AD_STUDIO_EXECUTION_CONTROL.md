# AI 开发执行控制协议（强制）

适用仓库：`konggu888/ecommerce-agent`；项目：`apps/ad-studio-desktop`。
战略路线唯一来源：`docs/AD_STUDIO_PRODUCT_ROADMAP.md`；验收来源：`docs/AD_STUDIO_ACCEPTANCE_PLAN.md` 与 `docs/AD_STUDIO_ACCEPTANCE_SOP.md`；总进度入口：`docs/AD_STUDIO_PROGRESS_DASHBOARD.md`。

## 一、计划层级
1. 产品路线图定义产品终点、模块边界、阶段顺序与阶段退出条件。
2. 阶段计划列出目标、任务、依赖、进入/退出条件、风险和暂缓项。
3. 功能计划定义输入/输出、状态变化、实际生产链、异常路径与可验证行为。
4. 单次任务单只授权本轮明确范围。
5. 验收证据记录测试、当前 SHA 的 CI/doc-sync 和真实环境证据。
6. 总进度台账记录唯一任务 ID、状态、依赖、权重、证据与剩余条件。

文件冲突时先停止受影响的工作，列明冲突并修订正式计划；不得自行选择最方便的解释。

## 二、每次“推进”前的强制步骤
1. 先读 `apps/ad-studio-desktop/SESSION_HANDOFF.md`。
2. 再读 AI handoff、本协议、总进度、路线图、验收计划/SOP、AGENTS、HELP 与 PROJECT_LOGIC。
3. 查 GitHub 实时 HEAD、PR #32 状态与 head SHA；PR #32 必须保持 Open / unmerged，禁止擅自合并。
4. 查当前 HEAD 的 CI Push、CI PR、docs-sync Push、docs-sync PR 四项；运行中不算通过，失败先读日志修复，旧 SHA 不能替代新 SHA。
5. 检查代码、测试、UI、文档和依赖，确认是否已有实现或存在阻断。
6. 从总进度台账选择唯一下一项；全量盘点未完成时先盘点，不得凭感觉挑新功能。
7. 开始修改前写明任务目标、范围、排除项、依赖、测试、文档、验收条件、失败处理与停止条件。

## 四、禁止联想式扩展
1. 每轮只做一个主要任务及必要依赖/阻断修复。
2. 非阻断的新问题只登记待办，说明影响与建议优先级，不顺手实现。
3. 不得为了功能数、测试数或“架构完整性”创造没有实际价值的任务。
4. 不得重复实现已有功能；先查代码、测试和证据。
5. 不得通过改名、反复拆分或追加无关验收点让任务无限延长。
6. 改变产品目标、阶段顺序、用户确认的约束或暂缓范围，必须先取得用户批准。
7. 满足预先验收条件即结束当前任务，其他改进另行排队。

## 五、开发与验收状态分开记录
开发状态：未盘点、未开始、进行中、代码完成、阻塞、暂缓、取消。
验收状态：未验收、自动化待运行、自动化失败、自动化通过、模块集成通过、模拟端到端通过、待真实环境验收、正式验收通过、部分通过。
代码已写但测试未运行不得标记自动化通过；CI 只支持当前 SHA 覆盖的自动化结论；暂缓项仍保留在范围内，不能默默从分母删除或当作通过。

## 六、任务和阶段的停止条件
任务满足预定功能条件、实际生产链接通、必要测试通过、当前 SHA 四项 CI/doc-sync 成功、文档同步、未验证边界和回退路径均已记录，才可标记“自动化阶段完成”。阶段必须逐条满足路线图退出条件，否则保持进行中并列出缺口。

## 七、文档同步
桌面代码/测试改动必须同一提交更新：AGENTS.md、HELP.md、PROJECT_LOGIC.md、验收计划、验收 SOP、SESSION_HANDOFF.md、AI handoff、未来功能备忘。路线图变化时同时更新路线图。规划体系变更应同步受影响入口；避免无意义地重复追加同一状态。

## 八、用户约束
PR #32 不合并。Windows 真机、真实素材、真实 Provider、实际扣款/账单核对、剪映现场、真实投放数据和商业效果验收继续暂缓，除非用户明确允许。最终输出最低 1080P 级：竖屏 1080×1920、横屏 1920×1080、方形 1080×1080；像素放大不等于细节恢复。

## 九、每轮结束报告
报告任务 ID、范围、实际修改、测试/失败修复、最新 SHA、四项 CI/doc-sync、PR 状态、开发/验收状态、未完成/暂缓项、台账变化和下一项正式任务。没有执行的测试不得声称通过。


## 十、用户体验与产品安全完整性审查（PLAN-003 子工作流）
用户提出用户体验、用户使用闭环和功能安全可能尚未被完整规划。执行代理必须先阅读 `docs/AD_STUDIO_USER_EXPERIENCE_SAFETY_AUDIT.md`，按该文档执行 UXS-1 至 UXS-5，并将其与 A0–A112 的既有任务映射合并，不另起冲突路线图。

- 审查至少覆盖首次使用/可发现性、完整用户旅程、费用/外部副作用、数据/素材/版本安全、商品真实性/合规/交付、跨功能依赖、异常解释/恢复、用户可理解状态与商业成片质量。
- 任何发现先分类为已有覆盖、相关但合同不同、重复候选、文档冲突、证据不足或候选独立缺口；未核实前不新增编号、不删改现有编号、不开发功能。
- P0/P1 风险必须显式登记缓解状态、代码/测试证据、UI反馈和剩余真实环境限制。未知不能当作安全。
- 用户体验与安全审查属于规划/证据审计，不能把静态映射或 CI 绿灯写成正式验收通过。
- 现有真实环境暂缓范围和 PR #32 不合并约束保持不变；总体完成率继续关闭。

## 十一、权威状态源与冲突裁决（强制，2026-10-15）

1. `docs/AD_STUDIO_PROGRESS_DASHBOARD.md` 是**唯一权威进度源**：唯一当前任务、下一项、任务状态、依赖、权重、证据状态均以其顶部当前状态与规范化台账为准。
2. `apps/ad-studio-desktop/SESSION_HANDOFF.md` 和 `docs/AD_STUDIO_AI_HANDOFF.md` 只保留接手必需的短摘要、当前 HEAD/CI/PR 状态和指向总台账的链接；不再独立定义另一套当前下一项。历史快照必须标注“历史/不可执行”。
3. `docs/AD_STUDIO_PRODUCT_ROADMAP.md` 只决定产品战略、阶段顺序和阶段退出条件；`docs/AD_STUDIO_ACCEPTANCE_PLAN.md` 决定正式验收范围；`docs/AD_STUDIO_ACCEPTANCE_SOP.md` 决定验收方法；`docs/AD_STUDIO_EXECUTION_CONTROL.md` 与 `AGENTS.md` 决定 AI 执行规则。它们不能覆盖总台账中的当前执行顺序。
4. `HELP.md`、`PROJECT_LOGIC.md`、代码和测试用于验证功能/实现事实，不是进度源。未来备忘与 UX/安全审计必须映射回既有任务台账，不得单独产生并行路线。
5. 若文件出现冲突，AI 必须暂停受影响任务，在总台账记录冲突来源、影响、裁决依据和修正动作；禁止自行挑选方便的“下一项”、重复执行旧任务或因新发现直接扩展范围。
6. 每轮只允许一个当前任务。完成条件满足即停止；新发现先登记，除非构成阻断，不顺手实现。所有进度和完成结论必须绑定可复核证据。

## 十二、CI 证据快照与防循环规则（强制，2026-10-15）

1. CI/doc-sync 结果属于**特定 SHA 的证据**，不是永久状态。执行前实时查询当前 HEAD；旧 SHA 绿灯不得继承。
2. 接手文件可以记录“本轮修改前核验基线 SHA 及其检查结果”，但必须明确它是基线快照，不能描述为正在编辑的提交已经通过。
3. 不得为了把刚查到的 CI 结果写回接手文档而反复追加提交、再触发新 CI、再写新结果。这会形成自我引用循环。最终提交的 CI 结果由 GitHub 实时状态和本轮执行报告记录；下一轮开始时再实时查询该 SHA。
4. 文档只在有实质状态/规则变化时更新，不因每次查询结果重复追加一段历史。历史证据按原样保留并标记，不伪装成当前状态。

## 十三、七层结果证明标准（全项目适用，强制）

所有任务的完成结论必须按适用范围区分以下结果层级，不得把低层级证据当成高层级结论：

1. 软件运行正确；
2. 功能行为正确；
3. 端到端流程正确；
4. 普通用户可用；
5. 商品表达真实、安全；
6. 商业成片质量达标；
7. 真实商业效果有效。

执行要求：
- 在唯一进度台账中为每项任务记录适用层级、证据类型/链接、证据绑定 SHA、可支持的结论、证据局限、剩余验证和暂缓状态。
- CI 只证明其实际执行的自动化检查结果，不自动证明用户可用、真实素材质量、真实 Provider 行为、商业成片质量或投放效果。
- 分辨率达到 1080P 不等于真实细节增强；视觉上令人满意不等于商品结构/功能真实；成片质量通过不等于实际商业效果有效。
- 真实环境、真实 Provider/扣费、Windows 机器、剪映现场和实际投放未执行时，必须标记为待验证/暂缓，不能用模拟测试、静态审查或文档规则代替。
- 七层标准是跨任务的证据分类体系，不是新增正式验收编号，也不能自行扩展 A0–A112 的范围。具体任务仍以正式验收计划和唯一进度台账为准。

## 十四、用户自由度与明确授权（强制，纳入 PLAN-003）

用户自由度必须与七层结果证明标准一起映射到唯一进度台账；它不是新的平行路线，也不新增/删除/重编号 A0–A112。执行前先读取 docs/AD_STUDIO_USER_EXPERIENCE_SAFETY_AUDIT.md 的 UXS-2 证据和风险，再将每项对应到既有正式验收合同。

审查必须覆盖：
1. **选择自由**：按功能选模型、配置文本/图像/视频/语音 Provider、本地服务与 Token 中转站；准确说明协议和能力边界，不承诺任意模型/端点都可直接接入。
2. **控制自由**：用户决定调用、继续、费用接受与自动回退。用户显式选择的模型/Provider/本地模式不可用时，不得在用户不知情的情况下切换到其他模型或将素材/提示词发往云端。
3. **知情自由**：外部调用前说明目标服务/数据目的地、发送的数据类别、预计费用与估算局限。费用未知或缺少单价/usage 时不得伪装成确定的零成本；UI 密钥掩码不得被描述为安全存储。
4. **撤回与纠正自由**：用户取消或拒绝时必须停止本次调用；适用场景应有测试证明外部调用次数为 0。核对失败恢复、模型切换后的项目/缓存/历史隔离及用户可理解的状态提示。

台账证据至少记录自由度维度、正式 ID 与来源、UI 入口、实际调用链、授权/拒绝/回退行为、费用与数据披露、密钥保存方式、缓存/历史隔离、正反例测试、证据 SHA、剩余风险及真实环境暂缓状态。文本模型可路由不等于图像/视频/语音阶段都可任意切换；静态代码或 CI 不能替代真实 Provider、代理站和账单验证。

当前 UXS-2 已发现的费用授权时点、自动回退/云端外发、密钥明文落盘、费用估算低估、数据去向告知、Provider 兼容边界和路由测试覆盖问题，先映射到 A0–A112 并裁决现有合同是否覆盖；完成全量语义去重前不得自行创建正式编号。真实 Provider、代理站、实际扣费/账单与 Windows 真机仍按用户要求暂缓。不得因纳入该维度而启动产品功能开发或计算整体完成率。
