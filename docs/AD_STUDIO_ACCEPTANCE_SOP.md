# AI 商品广告工厂｜标准验收操作规程

> 本文件是项目的**长期验收 SOP**。以后任何 AI、Codex 或开发代理收到“验收”“重新验收”“独立验收”“从头验收”等指令时，必须按本规程执行。
>
> **核心原则：验收结论必须来自本次对当前代码的实际检查，不能从聊天记录、旧 CI、旧验收记录或上一轮“通过”直接继承。**

## 1. 验收前：先确定范围

1. 找到正式验收计划：`docs/AD_STUDIO_ACCEPTANCE_PLAN.md`。
2. 确认当前要验收的正式阶段，例如 A18、A19 或 A20–A23。
3. 不得自行新增、拆分、合并正式阶段；必须以验收计划为准。
4. 明确本轮基线：从当前 main 最新提交开始，或者从明确指定的验收分支开始。
5. 明确本轮要验证的是：
   - 功能是否真实存在；
   - 数据/状态是否正确；
   - 异常路径是否正确；
   - 安全边界是否正确；
   - 文档是否同步；
   - CI 是否通过。
6. 如果用户要求“从头验收”，必须重新执行本规程，不能拿以前的测试结果当作本轮证据。

## 2. 第一步：检查当前状态

在开始写测试或判断通过之前，先检查：

### 2.1 Git 状态

- 当前分支。
- 当前 main 最新提交。
- 当前验收代码基线。
- 是否存在未合并修改。
- 是否有其他 PR 正在改变同一模块。

### 2.2 CI / GitHub Actions

必须查**当前验收提交对应的最新运行结果**。

检查：
- CI 是否成功。
- 是否仍在 queued / running。
- 是否失败。
- doc-sync 是否成功。
- 是否存在失败 job。

**禁止：**
- 用旧提交 CI 证明新提交通过。
- 把 queued/running 当成通过。
- 看到 PR 页面以前绿过，就直接宣布本次通过。

## 3. 第二步：如果失败，必须先定位

只要最新相关检查失败：

1. 打开失败 workflow。
2. 找到失败 job。
3. 读取失败日志。
4. 定位到具体测试、文件、函数或检查项。
5. 判断属于：
   - 生产代码问题；
   - 测试代码/夹具问题；
   - 文档同步问题；
   - 环境/依赖问题；
   - CI 配置问题。
6. 修复后重新运行。
7. **修复后的最新提交必须重新检查最新 CI。**

禁止“看起来应该没问题”式验收。

## 4. 第三步：从代码反推验收点

不要只看 PR 标题或开发者描述。

对本阶段实际代码进行检查：

- 输入从哪里来？
- 决策在哪里发生？
- 执行在哪里发生？
- 状态保存在哪里？
- 输出在哪里产生？
- 失败状态在哪里保存？
- 安全闸门在哪里？
- 数据边界在哪里？
- 哪些是真接通？
- 哪些只是接口、stub、placeholder、模拟夹具？

发现“代码存在但实际没接通”时，必须按**未实现/有条件通过**处理，不能算完成。

## 5. 第四步：建立本阶段专项测试

每个正式阶段都必须有与其目标直接对应的专项测试。

专项测试至少覆盖：

### 正常路径
验证功能确实能完成预期动作。

### 异常路径
人为制造失败，例如：
- 输入缺失；
- 路径失效；
- 文件损坏；
- 模型返回无效结果；
- 输出失败；
- 状态异常。

验证系统不会把失败伪装成成功。

### 边界/数据隔离
验证：
- 不同项目不串数据；
- 不同版本不串状态；
- 用户输入与 AI 推断分离；
- 模拟数据与真实数据分离；
- 真实外部数据没有被系统凭空生成。

### 安全拦截
如果本阶段涉及事实、合规、风险或真实写操作，必须验证危险状态能够被阻断。

### 回归
专项测试不能破坏已有主线；必须进入现有 Desktop Core 测试集合。

## 6. 第五步：测试必须尽量独立

验收测试应尽量：

- 从当前代码重新构造项目/输入；
- 使用确定性测试夹具；
- 不依赖真实广告平台；
- 不依赖不可控外部网络；
- 不依赖某台固定显卡；
- 不依赖本次聊天上下文；
- 不读取上一轮测试生成的“成功结果”作为本轮依据。

如果必须使用 mock / fixture，必须明确写出**测试夹具替代了什么真实能力**。

例如：

> 本次用确定性媒体夹具验证流程逻辑，不能证明 Windows 真机、真实剪映或真实 Provider 已接通。

## 7. 第六步：运行完整检查矩阵

验收提交后至少检查：

1. Desktop Core 测试
2. Python 语法
3. 前端语法
4. Typecheck
5. Engine
6. Risk Controller
7. 全套 CI
8. doc-sync
9. 与本阶段相关的专项测试

如果仓库当前还有其他强制检查，也必须纳入。

## 8. 第七步：文档同步

验收通过前必须检查：

- `AGENTS.md`
- `apps/ad-studio-desktop/HELP.md`
- `apps/ad-studio-desktop/PROJECT_LOGIC.md`
- `docs/AD_STUDIO_ACCEPTANCE_PLAN.md`

如果是未来功能或路线，还要检查：

- `docs/AI_AD_STUDIO_FUTURE_FEATURE_MEMO.md`

要求文档与实际代码一致。

**不能通过修改文档来掩盖代码没有实现。**

## 9. 第八步：失败后的固定循环

只要任何一项失败：

**失败**
→ **读取日志**
→ **定位具体原因**
→ **修改**
→ **重新测试**
→ **重新提交**
→ **重新检查最新 CI**
→ **重新检查 doc-sync**
→ **全部通过后才继续**

不能：

**失败 → 猜原因 → 继续开发下一阶段。**

## 10. 第九步：正式验收结论

只有满足以下条件才能写“通过”：

- 本阶段专项测试通过；
- 相关完整回归通过；
- CI 最新运行通过；
- doc-sync 最新运行通过；
- 代码与文档一致；
- 没有未处理的已知失败；
- 数据边界明确；
- 没有把模拟能力冒充真实能力。

如果只有离线单元测试通过，而真实模型、真实素材、Windows 真机、剪映或外部平台尚未验证，应写：

**有条件通过**

并明确哪些部分仍未验证。

## 11. 第十步：记录证据

正式验收记录至少写：

- 阶段
- 验收范围
- 验收基线/提交 SHA
- 专项测试入口
- 正常路径结果
- 异常路径结果
- 数据边界结果
- 安全拦截结果
- Desktop Core 测试结果
- CI 编号/结果
- doc-sync 编号/结果
- 发现的问题
- 修复提交
- 回归结果
- 是否真实能力
- 尚未验证的部分
- 最终结论
- 下一阶段

**不能只写“测试通过”。**

## 12. “独立重新验收”专用规则

用户如果说：

> “从头验收。”

或者：

> “重新验收，不要拿之前结果判断。”

必须：

1. 从当前代码基线重新开始。
2. 重新检查代码。
3. 重新执行专项测试。
4. 重新触发/确认当前提交的 CI。
5. 重新读取最新结果。
6. 不引用旧 CI 作为本轮通过依据。
7. 如果发现旧测试本身有问题，先修测试夹具，再重新验收。
8. 最终记录明确写“本次为独立重新验收”。

## 13. 多阶段验收规则

例如用户要求“验收 A20 到 A23”：

- 必须分别理解 A20、A21、A22、A23 的正式目标；
- 可以在一次 PR 中建立整组专项回归；
- 但最终记录必须分别说明每个阶段验证了什么；
- 不能因为 A20 通过就自动认为 A21–A23 通过；
- 必须确认整组专项测试覆盖所有阶段；
- 整组 CI 通过后才能宣布整组通过。

## 14. 验收完成后的推进

阶段正式通过后：

1. 更新 `docs/AD_STUDIO_ACCEPTANCE_PLAN.md` 的 checklist 和正式验收记录。
2. 如果未来备忘中存在已经正式实现的对应功能，从 `docs/AI_AD_STUDIO_FUTURE_FEATURE_MEMO.md` 删除。
3. 检查下一阶段目标。
4. **不要跳阶段。**
5. 进入下一阶段前，再执行一次“当前状态检查闸门”。

## 15. 永久禁止的验收错误

- 以前绿过，所以现在算绿。
- PR 能合并，所以功能算完成。
- 有测试，所以真实功能算完成。
- 有接口，所以 Provider 算接通。
- 有 mock，所以 Windows/剪映真机算完成。
- 有模拟数据，所以真实投放数据算完成。
- 文档写完成，所以代码算完成。
- CI 还在跑，所以可以宣布通过。
- CI 失败但没读日志就猜原因。
- 测试夹具失败却修改生产代码硬凑。
- 一个阶段通过就顺手宣布后续阶段全部通过。
- 用户要求重新验收，却引用旧验收结论。

## 16. 一句话执行口令

以后 AI 收到：

**“验收 X”**

执行：

**读正式计划 → 查当前基线 → 查最新 CI → 读失败日志 → 查代码 → 建专项测试 → 跑完整回归 → 查 doc-sync → 修失败 → 重跑最新 CI → 记录证据 → 正式结论 → 通过后再进入下一阶段。**

# 附录 B｜完整验收的判定规则

### “全部验收通过”的定义

只有在 **A0–A35 + B1–B3** 全部达到各自真实验收条件后，才能称为：

> **整个项目全部验收通过。**

其中：
- 已实现阶段：必须重新检查当前代码是否仍满足原标准。
- 尚未实现阶段：不能打勾，必须明确“未实现”。
- 用户明确暂缓阶段：标记“暂缓”，不能冒充“通过”。
- 需要 Windows 真机、真实剪映、真实 Provider 或真实平台才能证明的能力：离线测试只能证明逻辑，不能代替真实验收。

### 完整验收输出必须给出

1. 总体进度：A0–B3
2. 每阶段：通过 / 有条件通过 / 不通过 / 未实现 / 暂缓
3. 每阶段专项测试
4. 本次实际 CI
5. 本次 doc-sync
6. 发现的问题
7. 修复提交
8. 回归结果
9. 真实能力与模拟能力边界
10. 未验证项目
11. 下一步严格按 A0→…→B3 顺序推进

### 完整验收口令

用户说：

**“把整个项目从头到尾重新验收。”**

AI 必须执行：

**A0 → A1 → A2 → A3 → A4 → A5 → A6 → A7 → A8 → A9 → A10 → A11 → A12 → A13 → A14 → A15 → A16 → A17 → A18 → A19 → A20 → A21 → A22 → A23 → A24 → A25 → A26 → A27 → A28 → A29 → A30 → A31 → A32 → A33 → A34 → A35 → B1 → B2 → B3**

不得因为历史上某阶段曾经通过，就跳过当前代码检查。

**任何一项失败：停止 → 定位 → 修复 → 回归 → 重新验收。**
